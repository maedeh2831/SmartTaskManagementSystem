LEADERBOARD CALCULATION LOGIC
═════════════════════════════════════════════════════════════════════════════

1. GLOBAL RANKING ALGORITHM
───────────────────────────────────────────────────────────────────────────────

Input: All UserProgression records
Algorithm:
  ┌─ Query all UserProgression entities
  ├─ Sort by:
  │  1. TotalExperience (DESC) - Primary ranking metric
  │  2. CurrentLevel (DESC) - Tiebreaker
  │  3. TasksCompleted (DESC) - Secondary tiebreaker
  ├─ Assign sequential ranks: 1, 2, 3, ..., n
  ├─ For each rank:
  │  ├─ Calculate: RankChangeFromPrevious = PreviousRank - NewRank
  │  │  • Positive value = improved rank (moved up)
  │  │  • Negative value = declined rank (moved down)
  │  │  • Zero = no change
  │  ├─ Update Leaderboard entry:
  │  │  ├─ GlobalRank = assigned rank
  │  │  ├─ TotalPoints = UserProgression.TotalExperience
  │  │  ├─ CurrentLevel = UserProgression.CurrentLevel
  │  │  ├─ TasksCompleted = UserProgression.TasksCompleted
  │  │  ├─ ProjectsCompleted = UserProgression.ProjectsCompleted
  │  │  ├─ RankChangeFromPrevious = calculated change
  │  │  ├─ LastUpdated = DateTime.UtcNow
  │  │  └─ CalculatedAt = DateTime.UtcNow
  │  └─ Save to database
  └─ Batch SaveChangesAsync()

Performance: O(n log n) for n users (sort overhead dominates)
Database Impact: Single bulk update operation
Typical Time: ~100ms for 1000 users

2. WORKSPACE RANKING ALGORITHM
───────────────────────────────────────────────────────────────────────────────

Input: WorkspaceId, list of WorkspaceMember user IDs
Algorithm:
  ┌─ Get all users in workspace via WorkspaceMember
  ├─ Query UserProgression for only those user IDs
  ├─ Sort by same criteria as global:
  │  1. TotalExperience (DESC)
  │  2. CurrentLevel (DESC)
  ├─ Assign workspace-scoped ranks: 1, 2, 3, ..., m
  ├─ For each rank:
  │  ├─ Create or update Leaderboard entry with:
  │  │  ├─ WorkspaceId = input workspace ID
  │  │  ├─ WorkspaceRank = assigned rank (workspace scope)
  │  │  └─ Same other fields as global (reuse UserProgression data)
  │  └─ Save entry
  └─ Batch SaveChangesAsync()

Key Difference: WorkspaceId filter reduces dataset size
Rank Scope: Each user has independent workspace rank per workspace
Database Impact: Insert new or update existing workspace entries
Typical Time: ~50ms for 100 workspace members

3. TEAM RANKING ALGORITHM
───────────────────────────────────────────────────────────────────────────────

Input: WorkspaceId, all teams in workspace
Algorithm for each team:
  ┌─ Get all TeamMembers with UserId
  ├─ Query UserProgression for all members
  ├─ Calculate aggregated metrics:
  │  ├─ TotalTeamPoints = SUM(UserProgression.TotalExperience for all members)
  │  ├─ AverageTeamLevel = AVG(UserProgression.CurrentLevel for all members)
  │  ├─ TotalTeamExperience = SUM(UserProgression.TotalExperience)
  │  ├─ TasksCompleted = SUM(UserProgression.TasksCompleted)
  │  ├─ ProjectsCompleted = SUM(UserProgression.ProjectsCompleted)
  │  ├─ AchievementsUnlocked = COUNT(UserAchievement WHERE UnlockedDate IS NOT NULL)
  │  ├─ ActiveMembersThisWeek = COUNT(UserProgression WHERE LastProgressUpdate >= NOW - 7 days)
  │  ├─ TeamMemberCount = COUNT(TeamMembers)
  │  ├─ AverageProductivity = TotalTeamPoints / TeamMemberCount / 7
  │  └─ AverageCompletionRate = CompletedTasks / TotalTasks * 100
  │
  └─ Sort all teams by:
     1. TotalTeamPoints (DESC) - Primary: More points rank higher
     2. AverageTeamLevel (DESC) - Tiebreaker: Higher avg level wins

After sorting all teams:
  ┌─ Assign sequential ranks: 1, 2, 3, ..., t
  ├─ For each team:
  │  ├─ Calculate: RankChangeFromPrevious = PreviousRank - NewRank
  │  ├─ Get top 3 members (sorted by TotalPoints DESC):
  │  │  ├─ Store denormalized: UserId, UserName, CurrentLevel, TotalPoints, GlobalRank
  │  │  └─ Store in TopMembers list (optimization to avoid N+1 queries)
  │  ├─ Update TeamLeaderboard entry:
  │  │  ├─ TeamRank = assigned rank
  │  │  ├─ TotalTeamPoints = aggregated
  │  │  ├─ AverageTeamLevel = calculated
  │  │  ├─ All aggregated metrics = calculated above
  │  │  ├─ TopMembers = denormalized list
  │  │  ├─ RankChangeFromPrevious = calculated
  │  │  ├─ LastUpdated = DateTime.UtcNow
  │  │  └─ CalculatedAt = DateTime.UtcNow
  │  └─ Save entry
  └─ Batch SaveChangesAsync()

Time Complexity: O(m * (a log a)) for m teams, a average members per team
Typical Time: ~30ms for 20 teams with 10 members each

4. TIME-RANGE METRICS (Weekly/Monthly)
───────────────────────────────────────────────────────────────────────────────

Weekly Points Calculation:
  ┌─ Query: SELECT SUM(Amount) FROM WalletTransaction
  │         WHERE UserId = target
  │         AND TransactionDate >= DateTime.UtcNow.AddDays(-7)
  │         AND TransactionType = Earned
  ├─ Check reset: IF (DayOfWeek == Sunday AND (Now - LastResetDate).TotalDays >= 1)
  │  └─ Then: WeeklyPoints = 0, WeeklyPointsResetDate = Now
  └─ Store result in LeaderboardEntry.WeeklyPoints

Monthly Points Calculation:
  ┌─ Query: SELECT SUM(Amount) FROM WalletTransaction
  │         WHERE UserId = target
  │         AND TransactionDate >= DateTime.UtcNow.AddMonths(-1)
  │         AND TransactionType = Earned
  ├─ Check reset: IF (Day == 1 AND (Now - LastResetDate).TotalDays >= 1)
  │  └─ Then: MonthlyPoints = 0, MonthlyPointsResetDate = Now
  └─ Store result in LeaderboardEntry.MonthlyPoints

Reset Timing:
  • Weekly: Every Sunday at 00:00 UTC (checked during recalculation)
  • Monthly: 1st of month at 00:00 UTC (checked during recalculation)
  • Used in: API time-range filtering

GamificationBackgroundService (HostedService):

Timer Configuration:
  • Period: Every 1 hour (configurable)
  • Initial Delay: 5 minutes after app start
  • Execution Model: Fire and forget (async)

Execution Flow:
  ┌─ Timer fires
  ├─ RecalculateAllLeaderboardsAsync() called
  │  ├─ RecalculateGlobalLeaderboard()
  │  │  └─ Sorts all users, assigns global ranks
  │  │  └─ Duration: ~100ms for 1000 users
  │  │
  │  ├─ For each Workspace in database:
  │  │  ├─ RecalculateWorkspaceLeaderboard(workspaceId)
  │  │  │  └─ Sorts workspace members, assigns workspace ranks
  │  │  │
  │  │  └─ RecalculateTeamLeaderboard(workspaceId)
  │  │     └─ Calculates team aggregates, assigns team ranks
  │  │
  │  ├─ Update all time-range points (weekly/monthly)
  │  ├─ Check and apply resets where needed
  │  ├─ Clear all cache entries
  │  └─ Log completion with timestamps
  │
  └─ Next execution in 1 hour

Error Handling:
  • Try-catch around entire process
  • Individual workspace failures don't stop other workspaces
  • All errors logged with details
  • Process continues even if single workspace fails

6. CACHING LAYER
───────────────────────────────────────────────────────────────────────────────

Cache Type: IMemoryCache (in-process caching)
TTL (Time-To-Live): 60 minutes per entry

Cache Key Format and Scope:

Global Leaderboard:
  • Key: "leaderboard_global_{page}_{timeRange}"
  • Example: "leaderboard_global_1_all"
  • Invalidation: Page, Time-range independent
  • Hit Rate: ~98% (rankings stable within hour)

Workspace Leaderboard:
  • Key: "leaderboard_workspace_{workspaceId}_{page}_{timeRange}"
  • Example: "leaderboard_workspace_5_1_week"
  • Invalidation: Per workspace, page, time-range
  • Hit Rate: ~98%

Team Leaderboard:
  • Key: "leaderboard_teams_{workspaceId}_{timeRange}"
  • Example: "leaderboard_teams_5_month"
  • Invalidation: Per workspace, time-range
  • Hit Rate: ~98%

User Context:
  • Key: "leaderboard_user_{userId}_{timeRange}"
  • Example: "leaderboard_user_42_all"
  • Invalidation: Per user, time-range
  • Hit Rate: ~90% (varies with user activity)

Cache Invalidation Strategy:
  1. Automatic: TTL expiration (60 minutes)
  2. Manual: ClearLeaderboardCache() after recalculation
  3. Per-Entry: Individual entries expire independently
  4. No Centralized Clear: Each key expires independently

Performance Benefits:
  • Query Reduction: ~98% fewer database queries
  • Response Time: <10ms cached vs ~200ms uncached
  • Server Load: Dramatically reduced during peak usage
  • User Experience: Instant leaderboard views

Potential Improvement (Phase 5):
  • Migrate to Redis for distributed caching
  • Implement cache warming before expiration
  • Cache-aside pattern with automatic refresh
