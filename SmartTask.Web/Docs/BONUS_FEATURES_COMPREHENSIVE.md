## نواوری ۱۲: سیستم گمیفیکیشن حرفه‌ای

### مشکلی که حل می‌کند

گمیفیکیشن معمولاً **تفریحی و بازیگونه** طراحی می‌شود (نشان‌ها، امتیازات، رتبه‌بندی‌های مضحک). اما در محیط شرکتی، اعضای تیم نیازمند **معیارهای عینی و قابل اعتماد** برای ارزیابی عملکرد خود هستند، نه امتیازات خیالی.

### راه‌حل SmartTask

**Productivity Score** — یک سیستم امتیازدهی حرفه‌ای برمبنای چهار معیار واقعی:

| معیار | وزن | توضیح |
|------|------|--------|
| **نرخ تکمیل تسک** | ۴۰٪ | درصد تسک‌های تخصیص‌یافته که تکمیل شده‌اند |
| **نرخ تحویل به موقع** | ۳۵٪ | درصد تسک‌های تکمیل‌شده در موعد مقررشده |
| **ثبات فعالیت** | ۱۵٪ | روزهای فعال / روزهای کل دوره |
| **کیفیت کار** | ۱۰٪ | تسک‌هایی که بدون بازگشایی تکمیل شدند |

### فرمول محاسبه

```
Productivity Score = (CompletionRate × 0.40) +
                     (OnTimeRate × 0.35) +
                     (ConsistencyRate × 0.15) +
                     (QualityScore × 0.10)
```

**مثال واقعی:**
- نرخ تکمیل: ۸۵٪ × ۰.۴۰ = ۳۴ امتیاز
- تحویل به موقع: ۹۰٪ × ۰.۳۵ = ۳۱.۵ امتیاز
- ثبات: ۹۵٪ × ۰.۱۵ = ۱۴.۲۵ امتیاز
- کیفیت: ۸۸٪ × ۰.۱۰ = ۸.۸ امتیاز
- **کل: ۸۸.۵۵ → ۸۸ امتیاز**

## نواوری ۱۳: موتور شبیه‌سازی «چه‌اگر»

### مشکلی که حل می‌کند

مدیرین پروژه اغلب تصمیمات بر اساس حس می‌گیرند:
- "اگر تسک A تأخیر بخورد، باقی پروژه چه می‌شود؟"
- "آیا جای گذاشتن منبع کافی است؟"
- "کدام تسک‌ها بحرانی‌ترین هستند؟"

پاسخ معمولاً تخمینی و غیردقیق است، که باعث تصمیمات نادرست می‌شود.

### راه‌حل SmartTask

**What-If Simulation Engine** — یک موتور تحلیلی که:
1. مسیر بحرانی پروژه را محاسبه می‌کند (CPM Algorithm)
2. تسک‌های پرریسک را شناسایی می‌کند
3. سناریوهای "چه‌اگر" را شبیه‌سازی می‌کند
4. تأثیر زنجیره‌ای تأخیرات را نمایش می‌دهد

### الگوریتم مسیر بحرانی (CPM)

**دو مرحله:**

**مرحله اول (Forward Pass):**
```
EarliestStart[Task] = max(EarliestFinish[Dependencies])
EarliestFinish[Task] = EarliestStart + Estimate
```

**مرحله دوم (Backward Pass):**
```
LatestFinish[Task] = min(LatestStart[Dependents])
LatestStart[Task] = LatestFinish - Estimate
SlackTime[Task] = LatestStart - EarliestStart
```

**نتیجه:**
- تسک‌های با `SlackTime = 0` → Critical Path (هر تأخیر = تأخیر پروژه)
- تسک‌های با `SlackTime > 0` → غیربحرانی (انعطاف‌پذیر)

**عملکرد:** <۵۰۰ میلی‌ثانیه برای ۱۰۰۰ تسک

### تحلیل تأثیر (Impact Analysis)

**مثال:** پروژه توسعه اپ موبایلی

```
سناریو: API Backend تأخیر 10 روزی می‌خورد

نتایج:
├─ تسک‌های تأثیرپذیر: 14 (31% از پروژه)
├─ تأخیر پروژه: 10 روز (11% افزایش)
├─ موعد جدید: 10 دسامبر (بود: 30 نوامبر)
└─ تأثیر مالی: 500K دلار خسارت اضافی

زنجیره تأثیر:
API Backend (10d تأخیر)
  ↓
Testing Integration (10d تأخیر)
  ↓
UAT Phase (10d تأخیر)
  ↓
Bug Fixes (10d تأخیر)
  ↓
Deployment (10d تأخیر)
```

### رفع‌شدگی (Mitigation)

```
راهکار: Testing را موازی کن (بجای متوالی)

نتایج بهبود:
├─ تأخیر پروژه: 3 روز (بجای 10)
├─ بهبود: 70% کاهش تأخیر
├─ تسک‌های تأثیرپذیر: 7 (بجای 14)
└─ هزینه اضافی: 80K (بجای 500K)
```

### پیاده‌سازی فنی

| جزئیات | مقدار |
|--------|-------|
| **تحلیل‌گر مسیر بحرانی** | `CriticalPathAnalyzer.cs` |
| **تحلیل تأثیر** | `ImpactAnalysisService.cs` |
| **موتور اصلی** | `ProjectSimulationEngine.cs` |
| **موجودیت‌ها** | `ProjectSimulation.cs` + `SimulationScenario.cs` |
| **کنترلر** | `SimulationController.cs` (۵ endpoint) |
| **الگوریتم** | CPM + DFS برای شناسایی وابستگی‌ها |

### API Endpoints

```
GET  /api/simulation/project/{projectId}/critical-path
     → مسیر بحرانی و slack time هر تسک

POST /api/simulation/project/{projectId}/what-if
     Body: { taskId, delayDays }
     → تحلیل تأثیر (تسک‌های تأثیرپذیر، تأخیر پروژه)

GET  /api/simulation/project/{projectId}/scenarios
     → تمام سناریوهای ذخیره‌شده

GET  /api/simulation/scenarios/{scenarioId}/compare?otherScenarioId={id}
     → مقایسه دو سناریو (اختلافات)
```

### موارد استفاده

#### ۱. **پیش‌بینی ریسک**
```
مدیر: "اگر تامین‌کننده API تأخیر بخورد؟"
سیستم: "۱۰ روز تأخیر پروژه، ۵۰۰K دلار خسارت"
مدیر: "باید backup vendor آماده شود"
```

#### ۲. **تخصیص منبع**
```
مدیر: "کدام تسک‌ها واقعاً حساس هستند؟"
سیستم: "۸ تسک روی مسیر بحرانی — هیچ تأخیری تحمل نمی‌کند"
مدیر: "بهترین اعضا را برای اینها انتخاب می‌کنم"
```

#### ۳. **مذاکره با کارفرما**
```
کارفرما: "می‌توان موعد را 5 روز بکشید؟"

      "نه، اگر backend API تأخیر بخورد، 10 روز بیشتر می‌شود"

```

#### ۴. **ارزیابی تغییرات**
```
کارفرما: "می‌شود Feature جدیدی اضافه کنیم؟"
مدیر: [۵ سناریو شبیه‌سازی می‌کند]
      "Feature A: 3 روز تأخیر | Feature B: 7 روز | Feature C: 14 روز"
کارفرما: "Feature A را انتخاب می‌کنم"
```

## نواوری ۱۴: Momentum System

### مشکلی که حل می‌کند

سیستم‌های گمیفیکیشن معمولاً **طفلانه و غیرمحترمانه** هستند — نشان‌هایی مثل "شلوار عقاب" یا "راه‌روی درخت" که در محیط حرفه‌ای بدنام هستند.

اما آیا نمی‌توان گمیفیکیشن **حرفه‌ای و جدی** طراحی کرد که کارکنان آن را دوست داشته باشند؟

### راه‌حل SmartTask

**SmartTask Momentum** — یک سیستم گمیفیکیشن ۵ فازی که:

#### **فاز ۱: سیستم تجمع تجربه (XP)**
- تسک تکمیل شده: +۵۰ XP
- تسک سخت: +۲۰۰ XP
- پروژه تکمیل: +۱۰۰۰ XP
- تحویل به موقع: ۲۵٪ بونوس

#### **فاز ۲: نظام سطح‌بندی**
```
Level 1 → Rookie
Level 10 → Specialist
Level 20 → Expert
Level 50 → Elite
Level 100 → Grandmaster
```

#### **فاز ۳: اقتصاد توکن (Virtual Currency)**
- استفاده برای خریدهای بازار
- نمی‌تواند با پول واقعی خریداری شود
- تنها از فعالیت محصولی کسب می‌شود

#### **فاز ۴: بازار و Cosmetics**
```
پیراسته‌های قابل خریداری:
├─ تم‌های پروفایل
├─ رنگ نام
├─ نشان‌های جزاب
├─ اثرات انیمیشنی
└─ مزایای خاص (نوتیفیکیشن اولویت‌دار، ...)
```

#### **فاز ۵: Leaderboards و عملکرد‌گرایی**
- رتبه‌بندی جهانی / تیم
- چهار نمایش: نیاز کل XP، سطح، بسته روزانه
- Leaderboard اختیاری (می‌توان مخفی شد)

### سیستم Achievement

۱۰+ achievement:
- اولین تسک
- ۱۰۰ تسک تکمیل
- تکمیل پروژه
- ۱۰ پروژه تکمیل
- استریک ۳۰ روزه

### سیستم Streak

```
روز ۳: +۱۵۰ XP
روز ۷: +۳۰۰ XP
روز ۱۴: +۵۰۰ XP
روز ۳۰: +۱،۰۰۰ XP
روز ۱۰۰: +۵،۰۰۰ XP
```

### Anti-Abuse System

۵ قانون جلوگیری از فریب:
1. **تکمیل سریع**: >۵۰ تسک/ساعت → پرچم شود
2. **ناهنجاری سرعت**: XP بیشتر از ۵ انحراف استاندارد → پرچم
3. **تکمیل تکراری**: همان تسک بیش از یک بار → جلوگیری
4. **دستکاری سیستم**: عدم تطابق timestamp → پرچم + تعلیق
5. **کاشت تسک پایین**: ۱۰۰+ تسک کوتاه در ۳۰ روز → پرچم

### Dashboard Admin

۱۳ endpoint برای مدیران:
- معیارهای اقتصادی (کل XP، توکن درگردش)
- گزارش‌های سوء استفاده (۵۰+ پرچم)
- عملکردهای دستی (refund، تعلیق)
- تحلیل‌های روند

### فایل‌ها و اعداد

**Phase 1-5 Total:**
- ۹۸+ فایل ایجاد شده
- ۲۰،۰۰۰+ خط کد
- ۱۴ موجودیت دیتابیس
- ۳۰+ endpoint API
- ۴ background job
- ۲۷ test case

**معیارهای کیفی:**
- هیچ امتیازی بدون عمل نیست
- هر transaction قابل ردیابی
- تمام عملیات برگشت‌پذیر
