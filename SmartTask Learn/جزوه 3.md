## ۱. سطوح دسترسی Public/Private فضاهای کاری

### ۱.۱ مفهوم

در هنگام ایجاد یک Workspace (فضای کاری)، کاربر می‌تواند یکی از دو حالت زیر را انتخاب کند:

| حالت | نماد | توضیح |
|------|------|-------|
| **خصوصی (Private)** | 🔒 | فقط اعضای دعوت‌شده می‌توانند ببینند |
| **عمومی (Public)** | 🌍 | همه کاربران سامانه می‌توانند ببینند و بپیوندند |

### ۱.۲ پیاده‌سازی در کد

**تعریف Enum:**
```csharp
// Models/Enums/VisibilityType.cs
public enum VisibilityType
{
    Private = 1,
    Public = 2
}
```

**ذخیره در مدل Workspace:**
```csharp
// Models/Entities/Workspace.cs
public VisibilityType Visibility { get; set; } = VisibilityType.Private;
```

مقدار پیش‌فرض **Private** است.

**نمایش در رابط کاربری:**
- صفحه ایجاد و ویرایش Workspace → رادیوباتن "خصوصی/عمومی"
- لیست Workspace → نوشته "خصوصی" یا "عمومی" + آیکون قفل/گلوب
- صفحه جزئیات Workspace → نمایش وضعیت دسترسی

### ۱.۳ منطق کنترل دسترسی

متد مرکزی بررسی عضویت در `BaseController.cs`:
```csharp
protected async Task<bool> IsWorkspaceMemberAsync(
    ApplicationDbContext context, int workspaceId)
{
    return await context.ProjectMembers
        .AnyAsync(x => x.WorkspaceId == workspaceId
            && x.ApplicationUserId == CurrentUser.UserId
            && x.ViewState);
}
```

این متد در تمام کنترلرها استفاده می‌شود:
- `WorkspaceController.Details()` → اگر عضو نیستی، اجازه ورود نداری
- `ProjectController` → نیاز به عضویت
- `SprintController` → نیاز به عضویت

### ۱.۴ نکته مهم برای دفاع

> اگر استاد پرسید "آیا فرق واقعی بین Public و Private وجود دارد؟":
> 
> در نسخه فعلی، مقدار `Visibility` در دیتابیس ذخیره و در UI نمایش داده می‌شود. کنترل دسترسی واقعی بر اساس **عضویت** کاربر در Workspace است. برای نسخه‌های آینده، می‌توان قابلیت "مشاهده Workspace‌های عمومی توسط غیراعضا" و "پیوستن بدون دعوت" را اضافه کرد.

## ۲. ارتباط Backlog → Sprint → User Story → Task

### ۲.۱ ساختار سلسله‌مراتبی

SmartTask از مدل **Scrum** برای مدیریت تسک‌ها استفاده می‌کند. ساختار از بالا به پایین:

```
📁 Workspace (فضای کاری)
 └── 📂 Project (پروژه)
      ├── 📋 Backlog (فقط یکی به ازای هر پروژه)
      │    └── 📝 UserStory (آیتم‌های بک‌لاگ)
      │         └── ✅ Task (وظایف اجرایی)
      │              └── ☑️ SubTask (زیرتسک‌ها)
      │
      ├── 🏃 Sprint (اسپرینت‌ها)
      │    └── 📝 UserStory (آیتم‌های منتقل‌شده از بک‌لاگ)
      │
      └── 🚗 OffroadTask (کارهای خارج از دامنه)
```

### ۲.۲ توضیح هر لایه

#### Backlog (فقط یکی)
- هر پروژه **دقیقاً یک** Backlog دارد
- نام پیش‌فرض: `Product Backlog`
- نقش: محل ذخیره User Story هایی که هنوز به اسپرینتی تخصیص نداده‌اید
- فایل: `Models/Entities/Backlog.cs`

#### User Story (آیتم‌های بک‌لاگ)
- زیرمجموعه Backlog است (فیلد `BacklogId`)
- **می‌تواند** به یک Sprint تخصیص داده شود (فیلد `SprintId` که nullable است)
- اگر `SprintId = null` → هنوز در بک‌لاگ منتظر است
- اگر `SprintId` مقدار داشته باشد → به اسپرینت تخصیص داده شده
- فیلدهای کلیدی:
  - `StoryPoint` → اندازه کار (斐波那契: 1, 2, 3, 5, 8, 13)
  - `BusinessValue` → ارزش تجاری
  - `Priority` → اولویت
  - `Status` → New, Ready, InProgress, Done, Closed

#### Task (وظایف اجرایی)
- زیرمجموعه مستقیم UserStory است (فیلد `UserStoryId`)
- **هیچ ارتباط مستقیمی با Sprint ندارد** — از طریق UserStory به Sprint وصل می‌شود
- فیلدهای کلیدی:
  - `Estimate` → ساعت تخمینی کار
  - `StartDate`, `DueDate` → زمان شروع و پایان
  - `Status` → ToDo, InProgress, InReview, Done, Cancelled
  - `Type` → Task, Bug, Story, Epic
  - `Priority` → VeryLow, Low, Medium, High, VeryHigh

#### SubTask (زیرتسک‌ها)
- زیرمجموعه Task است (فیلد `TaskItemId`)
- ساده‌ترین سطح کار
- فقط `Title` و `IsCompleted` دارد

#### OffroadTask (خارج از دامنه)
- مستقیماً به Project وصل است (نه به Backlog یا UserStory)
- برای کارهای **خارج از دامنه رسمی پروژه** (مثل باگ فوری سرور)

### ۲.۳ فرآیند کاری (Workflow)

```
مرحله ۱: ایجاد User Story در Backlog
    └── SprintId = null (هنوز به اسپرینتی تخصیص ندارد)

مرحله ۲: انتقال User Story به Sprint (اسپرینت پلنینگ)
    └── SprintId = شماره اسپرینت مورد نظر

مرحله ۳: ایجاد Task زیر User Story
    └── هر User Story می‌تواند چندین Task داشته باشد

مرحله ۴: ایجاد SubTask زیر Task (اختیاری)
    └── هر Task می‌تواند چندین SubTask داشته باشد
```

### ۲.۴ مثال عملی

```
Backlog: Product Backlog
 └── User Story: "ورود کاربر به سامانه"
      ├── Sprint: "اسپرینت ۱" (تخصیص داده شده)
      ├── StoryPoint: 5
      └── Task‌ها:
           ├── Task: "طراحی فرم ورود"
           │    ├── SubTask: "ایجاد input ایمیل"
           │    ├── SubTask: "ایجاد input رمز عبور"
           │    └── SubTask: "دکمه ورود"
           ├── Task: "اعتبارسنجی سمت سرور"
           ├── Task: "اتصال به دیتابیس"
           └── Task: "تست ورود"
```

### ۲.۵ پاسخ به سوال رایج

> "وقتی می‌خوام یه کاری رو برای انجام بزنم تو سیستم باید چجوری تعریفش کنم؟"

| نوع کار | کجا تعریف کنید |
|---------|---------------|
| کار رسمی پروژه | User Story → در Backlog → سپس انتقال به Sprint |
| زیرکار یک User Story | Task (زیر User Story) |
| جزئیات یک Task | SubTask (زیر Task) |
| کار ضروری خارج از پروژه | OffroadTask (مستقل از بک‌لاگ) |

## ۳. نمودار Burndown و Velocity

### ۳.۱ نمودار Burndown (نرود کار)

**فایل:** `Services/Implementations/SprintService.cs` → متد `GetBurndownDataAsync`

**چیست؟** نمایش گرافیکی پیشرفت کار در طول یک اسپرینت. نشان می‌دهد هر روز چقدر کار باقی مانده.

**بر اساس چه شاخصی؟** Story Point (نه Task، نه ساعت)

**فرمول دقیق:**
```
خط ایده‌آل (خاکستری):
  IdealRemaining = TotalPoints - (TotalPoints / تعداد_کل_روزها × روز_های_سپری‌شده)

خط واقعی (بنفش):
  ActualRemaining = TotalPoints - مجموع_StoryPoint_هایی_که_تا_آن_روز_تمام_شده‌اند
```

**مثال عددی:** اسپرینت ۱۰ روزه با ۴۰ Story Point:

| روز | خط ایده‌آل | خط واقعی | توضیح |
|-----|-----------|----------|-------|
| روز ۱ | ۴۰ | ۴۰ | شروع |
| روز ۳ | ۳۲ | ۳۵ | کندتر از برنامه ⚠️ |
| روز ۵ | ۲۴ | ۲۰ | جلوتر از برنامه ✅ |
| روز ۱۰ | ۰ | ۵ | ۵ امتیاز مانده! |

**نکات کلیدی:**
- خط ایده‌آل: همیشه یک خط مستقیم از بالا به پایین (خط‌چین)
- خط واقعی: فقط تا **روز جاری** نمایش داده می‌شود
- پایین‌تر از خط ایده‌آل = جلوتر از برنامه ✅
- بالاتر از خط ایده‌آل = عقب‌تر از برنامه ⚠️

### ۳.۲ نمودار Velocity (سرعت)

**فایل:** `Services/Implementations/SprintService.cs` → متد `GetVelocityDataAsync`

**چیست؟** مقایسه کار برنامه‌ریزی‌شده با کار واقعی تکمیل‌شده در اسپرینت‌های گذشته.

**فرمول دقیق:**
```
PlannedPoints = مجموع StoryPoint تمام UserStory‌های اسپرینت
CompletedPoints = مجموع StoryPoint فقط UserStory‌هایی که Status = Done هستند
```

**فقط اسپرینت‌های Completed نمایش داده می‌شوند** (آخرین ۶ اسپرینت).

**مثال:**

| اسپرینت | برنامه‌ریزی‌شده | تکمیل‌شده | درصد تحقق |
|---------|---------------|-----------|----------|
| اسپرینت ۱ | ۳۰ SP | ۲۵ SP | ۸۳٪ |
| اسپرینت ۲ | ۴۰ SP | ۳۵ SP | ۸۷٪ |
| اسپرینت ۳ | ۳۵ SP | ۳۵ SP | ۱۰۰٪ |

### ۳.۳ مقایسه دو نمودار

| ویژگی | Burndown | Velocity |
|-------|----------|----------|
| مقطع زمانی | یک اسپرینت خاص | چند اسپرینت گذشته |
| نوع نمودار | خطی (Line) | میله‌ای (Bar) |
| هدف | پیشرفت لحظه‌ای | روند کلی عملکرد |
| شرط نمایش | اسپرینت User Story داشته باشد | حداقل یک اسپرینت Completed |

**کتابخانه رسم:** Chart.js 4.4.0  
**فایل جاوااسکریپت:** `wwwroot/js/agile-dashboard.js`  
**مسیر دسترسی:** منوی پروژه → Agile Dashboard

## ۴. تحلیل بار کاری (Workload Analysis)

### ۴.۱ چیست؟

نشان می‌دهد **هر عضو تیم چند ساعت کار تخصیص داده شده** در مقایسه با **ظرفیت هفتگی‌اش**.

**فایل:** `Services/Implementations/WorkloadAnalysisService.cs`  
**کنترلر:** `WorkloadController`

### ۴.۲ فرمول دقیق

```
AssignedHours = مجموع (Estimate هر Task ÷ تعداد اعضای تخصیص‌یافته به آن Task)

UtilizationPercent = (AssignedHours ÷ WeeklyCapacityHours) × 100
```

**مثال عددی:** عضوی با ۴۰ ساعت ظرفیت هفتگی:

| Task | Estimate | تعداد اعضا | سهم این عضو |
|------|----------|-----------|------------|
| طراحی فرم | ۸ ساعت | ۲ نفر | ۴ ساعت |
| تست API | ۱۲ ساعت | ۳ نفر | ۴ ساعت |
| باگ‌فیکس | ۶ ساعت | ۱ نفر | ۶ ساعت |
| **مجموع** | | | **۱۴ ساعت** |

```
Utilization = 14 ÷ 40 × 100 = 35%
StatusLevel = "under" (زیر 80%)
```

### ۴.۳ سه سطح وضعیت

| سطح | شرط | رنگ | معنی |
|-----|------|-----|------|
| `under` | کمتر از ۸۰٪ | 🟢 سبز | ظرفیت خالی دارد |
| `balanced` | ۸۰٪ تا ۱۰۰٪ | 🟡 زرد | بهینه |
| `overloaded` | بیشتر از ۱۰۰٪ | 🔴 قرمز | اضافه‌بار ⚠️ |

### ۴.۴ نمایش دوگانه

- **بارکاری کل پروژه** → تمام Task‌های باز پروژه
- **بارکاری اسپرینت فعال** → فقط Task‌های اسپرینت جاری

**قابلیت ویرایش:** مدیر پروژه می‌تواند ظرفیت هفتگی هر عضو را تغییر دهد.

## ۵. پیش‌بینی ریسک تأخیر (Delay Risk Prediction)

### ۵.۱ چیست؟

یک **امتیاز ریسک ۰ تا ۱۰۰** برای کل پروژه که احتمال تأخیر را نشان می‌دهد.

**فایل:** `Services/Implementations/DelayRiskService.cs`  
**کنترلر:** `RiskController`

### ۵.۲ چهار شاخص و وزن هرکدام

```
╔══════════════════════════════════════════════════════════╗
║  شاخص                         ║  وزن   ║  حداکثر امتیاز ║
╠══════════════════════════════════════════════════════════╣
║  ۱. نسبت Task‌های عقب‌افتاده   ║  40%   ║  ۴۰ امتیاز     ║
║  ۲. نسبت اعضای اضافه‌بار      ║  30%   ║  ۳۰ امتیاز     ║
║  ۳. زنجیره‌های پرریسک         ║  20%   ║  ۲۰ امتیاز     ║
║  ۴. فعالیت اخیر Cascade       ║  10%   ║  ۱۰ امتیاز     ║
╚══════════════════════════════════════════════════════════╝
```

### ۵.۳ فرمول دقیق

```
OverdueScore = (تعداد Task‌های عقب‌افتاده ÷ کل Task‌های باز) × 40
WorkloadScore = (تعداد اعضای overloaded ÷ کل اعضا) × 30
DependencyScore = min(تعداد زنجیره‌های پرریسک × 4, 20)
CascadeScore = min(تعداد cascade‌های ۷ روز اخیر × 2, 10)

RiskScore = min(OverdueScore + WorkloadScore + DependencyScore + CascadeScore, 100)
```

### ۵.۴ سطوح ریسک

| امتیاز | سطح | رنگ |
|--------|------|-----|
| ۰ تا ۲۵ | کم (Low) | 🟢 سبز |
| ۲۶ تا ۵۰ | متوسط (Medium) | 🟡 زرد |
| ۵۱ تا ۷۵ | بالا (High) | 🟠 نارنجی |
| ۷۶ تا ۱۰۰ | بحرانی (Critical) | 🔴 قرمز |

### ۵.۵ تحلیل متنی با هوش مصنوعی

با کلیک روی دکمه "تحلیل هوشمند"، داده‌های عددی به **LM Studio (Gemma)** ارسال می‌شود و یک تحلیل روایی ۳-۴ جمله‌ای فارسی تولید می‌شود. این قابلیت در `DelayRiskService.cs` با فراخوانی `_aiClient.GetCompletionAsync()` پیاده‌سازی شده است.

## ۶. شاخص سلامت پروژه (Project Health Score)

### ۶.۱ چیست؟

شاخص ترکیبی از چهار زیرشاخص که یک عدد نهایی (۰ تا ۱۰۰) از وضعیت کلی پروژه نشان می‌دهد.

**فایل:** `Services/Implementations/ProjectHealthService.cs`  
**کنترلر:** `HealthController`

### ۶.۲ چهار زیرشاخص و وزن هرکدام

```
╔═══════════════════════════════════════════════════════════╗
║  زیرشاخص                ║  وزن   ║  منبع محاسبه          ║
╠═══════════════════════════════════════════════════════════╣
║  ۱. سلامت زمان‌بندی      ║  30%   ║  درصد Task‌های به‌موقع  ║
║  ۲. سلامت بارکاری        ║  25%   ║  درصد اعضای overloaded ║
║  ۳. سلامت وابستگی‌ها     ║  25%   ║  زنجیره‌های پرریسک     ║
║  ۴. پیشرفت واقعی         ║  20%   ║  درصد تکمیل UserStory  ║
╚═══════════════════════════════════════════════════════════╝
```

### ۶.۳ فرمول دقیق

```
ScheduleHealth = (Task‌های به‌موقع ÷ کل Task‌های باز) × 30
WorkloadHealth = (اعضای سالم ÷ کل اعضا) × 25
DependencyHealth = (زنجیره‌های سالم ÷ کل زنجیره‌ها) × 25
ProgressHealth = (UserStory‌های Done ÷ کل UserStory‌های اسپرینت) × 20

HealthScore = ScheduleHealth + WorkloadHealth + DependencyHealth + ProgressHealth
```

### ۶.۴ نمایش رنگی

| امتیاز | رنگ | معنی |
|--------|-----|------|
| ۷۵ تا ۱۰۰ | 🟢 سبز | وضعیت عالی |
| ۵۰ تا ۷۴ | 🟡 زرد | نیاز به توجه |
| ۲۵ تا ۴۹ | 🟠 نارنجی | وضعیت نگران‌کننده |
| ۰ تا ۲۴ | 🔴 قرمز | بحرانی |

### ۶.۵ ارتباط بین سه تحلیل

```
Workload Analysis ──→ Delay Risk ──→ Project Health
Dependency Service ─┘         │
                              └──→ AI Narrative (متن تحلیلی)
```

- **Workload Analysis** داده خام بارکاری را تولید می‌کند
- **Delay Risk** از Workload + Dependency + Cascade استفاده می‌کند
- **Project Health** از Delay Risk + Delivery استفاده می‌کند

## ۷. سرویس SignalR — ارتباط بلادرنگ

### ۷.۱ SignalR چیست؟

**ASP.NET Core SignalR** یک کتابخانه مایکروسافت برای ایجاد **ارتباط بلادرنگ (Real-Time)** بین سرور و کلاینت است. بدون نیاز به رفرش صفحه، سرور می‌تواند مستقیماً به مرورگر پیام بفرستد.

**پروتکل‌های زیربنایی (خودکار):**
1. **WebSocket** (ترجیحی، بهترین کارایی)
2. **Server-Sent Events** (پشتیبان)
3. **Long Polling** (آخرین گزینه)

### ۷.۲ چرا SignalR در SmartTask استفاده شده؟

در پروژه‌های مدیریت تسک، کاربران نیاز دارند **بدون رفرش صفحه** از تغییرات مطلع شوند:
- اعلان جدید رسید
- پیام چت جدید ارسال شد
- کسی آنلاین/آفلاین شد
- کسی دارد تایپ می‌کند

Without SignalR، باید هر چند ثانیه سرور را Polling می‌کرد (XHR Request) که هم کند است و هم سرور را تحت فشار می‌گذارد.

### ۷.۳ دو Hub در پروژه

**نحوه کار:**
1. کاربر وصل می‌شود → به گروه `user-{userId}` اضافه می‌شود
2. هر کاربر فقط اعلان‌های خودش را دریافت می‌کند
3. سرور از طریق `IHubContext<NotificationHub>` به گروه کاربر پیام می‌فرستد

- `CreateAsync()` → ارسال اعلان تکی
- `BatchCreateAsync()` → ارسال دسته‌ای اعلان‌ها

**کجا استفاده می‌شود (کلاینت):**


## ۸. سرویس ایمیل — Gmail SMTP

### ۸.۱ SMTP چیست؟

**SMTP** (Simple Mail Transfer Protocol) پروتکل استاندارد ارسال ایمیل است. وقتی می‌خواهید از طریق کد ایمیل بفرستید، باید به یک **سرور SMTP** وصل شوید.

**پیکربندی در SmartTask:**
- **Host:** `smtp.gmail.com`
- **Port:** `587` (STARTTLS)
- **SSL:** فعال
- **اعتبارنامه:** ایمیل Gmail + App Password

### ۸.۲ چرا Gmail SMTP؟
- **رایگان** (تا ۵۰۰ ایمیل در روز)
- **قابل اطمینان** (سرور گوگل)
- **بدون نیاز به سرور اختصاصی**

### ۸.۳ معماری سرویس

```
📂 Services/Email/
   ├── IEmailService.cs      ← اینترفیس
   ├── EmailService.cs       ← پیاده‌سازی
   └── EmailSettings.cs      ← تنظیمات
```

**`EmailSettings.cs`:**
```csharp
public class EmailSettings
{
    public string Host { get; set; }      // smtp.gmail.com
    public int Port { get; set; }          // 587
    public string Email { get; set; }      // آدرس Gmail
    public string Password { get; set; }   // App Password
    public bool EnableSsl { get; set; }    // true
}
```

**`EmailService.cs`:**
```csharp
public async Task SendEmailAsync(string to, string subject, string body)
{
    using var client = new SmtpClient(_settings.Host, _settings.Port);
    client.EnableSsl = _settings.EnableSsl;
    client.Credentials = new NetworkCredential(_settings.Email, _settings.Password);
    
    var message = new MailMessage
    {
        From = new MailAddress(_settings.Email),
        Subject = subject,
        Body = body,
        IsBodyHtml = true   // متن HTML
    };
    message.To.Add(to);
    await client.SendMailAsync(message);
}
```

### ۸.۴ کجاها ایمیل ارسال می‌شود؟ (۴ مورد)

| # | مورد | فایل | موضوع ایمیل |
|---|------|------|-------------|
| ۱ | تایید ایمیل هنگام ثبت‌نام | `AccountController.cs` → `Register` | "تایید ایمیل SmartTask" |
| ۲ | بازیابی رمز عبور | `AccountController.cs` → `ForgotPassword` | "بازیابی رمز عبور" |
| ۳ | دعوت به Workspace | `WorkspaceInvitationService.cs` | "دعوت به فضای کاری" |
| ۴ | تست ایمیل | `AccountController.cs` → `TestEmail` | "SmartTask Test" |

### ۸.۵ جریان کامل (مثال: دعوت به Workspace)

```
۱. مدیر "دعوت عضو جدید" را کلیک می‌کند
         ↓
۲. WorkspaceInvitationService.InviteAsync()
         ↓
۳. رکورد دعوت در دیتابیس (توکن + انقضای ۳ روز)
         ↓
۴. _emailService.SendEmailAsync()
         ↓
۵. SmtpClient → smtp.gmail.com:587
         ↓
۶. ایمیل HTML با لینک دعوت ارسال می‌شود
         ↓
۷. کاربر ایمیل را دریافت و روی لینک کلیک می‌کند
         ↓
۸. وارد صفحه ثبت‌نام/پذیرش دعوت می‌شود
```

## ۹. سرویس هوش مصنوعی — LM Studio

### ۹.۱ LM Studio چیست؟

**LM Studio** یک نرم‌افزار محلی (Local) برای اجرای مدل‌های زبانی (LLM) روی سرور خودتان است. برخلاف OpenAI API که پولی است و داده‌ها به سرور خارجی می‌رود، LM Studio روی **سرور شما** اجرا می‌شود.

**پیکربندی SmartTask:**
- **آدرس:** `http://92.246.145.99:1234/v1/chat/completions`
- **مدل:** `google/gemma-4-12b`
- **فرمت API:** سازگار با OpenAI API

### ۹.۲ چرا LM Studio و نه OpenAI؟

| معیار | OpenAI API | LM Studio |
|-------|-----------|-----------|
| هزینه | پولی | رایگان |
| حریم خصوصی | داده به خارج | محلی |
| محدودیت | Rate Limit | بدون محدودیت |

### ۹.۳ معماری سرویس

```
📂 Services/AI/
   ├── IAiClientService.cs    ← اینترفیس
   ├── AiClientService.cs     ← پیاده‌سازی

```

**`OpenAiSettings.cs`:**
```csharp
public class OpenAiSettings

}
```

**`IAiClientService.cs`:**
```csharp

{
```

## ۱۰. سرویس Webpushr — Push Notification

### ۱۰.۱ Push Notification چیست؟

پیامی است که **خارج از مرورگر** و حتی وقتی صفحه بسته است به کاربر نمایش داده می‌شود.

**تفاوت با SignalR:**

| ویژگی | SignalR | Webpushr |
|-------|---------|----------|
| شرط نمایش | مرورگر باز باشد | حتی بسته باشد |
| نوع ارتباط | WebSocket (بلادرنگ) | HTTP Push (یک‌طرفه) |
| کاربرد | چت + اعلان درون‌برنامه‌ای | اعلان خارج از مرورگر |
| نیاز به اجازه کاربر | خیر | بله |

### ۱۰.۲ Webpushr چیست؟

یک سرویس Push Notification رایگان (تا ۱۰,۰۰۰ مشترک) با API ساده.

**آدرس API:** `https://api.webpushr.com/v1/notification/send/sid`

### ۱۰.۳ معماری سرویس

```
📄 Services/Implementations/WebpushrService.cs
📄 Services/Interfaces/IWebpushrService.cs
```

**سه متد اصلی:**

| متد | کاربرد |
|-----|--------|
| `SendChatMessagePushAsync()` | اعلان پیام چت به سایر اعضای پروژه |
| `SendTestPushAsync()` | اعلان آزمایشی برای تست |
| `SendWebpushrNotification()` | ارسال HTTP به API Webpushr |

### ۱۰.۴ کجاها استفاده می‌شود؟ (۲ مورد)

**۱. اعلان پیام چت جدید:**
```csharp
// ChatHub.cs → SendMessage()
await Clients.Group(GetProjectGroupName(projectId))
    .SendAsync("ReceiveMessage", message);  // SignalR (آنلاین)

await _webpushrService.SendChatMessagePushAsync(...);  // Webpushr (آفلاین)
```

**۲. تست Push:**
```csharp
// ChatHub.cs → TestPush()
await _webpushrService.SendTestPushAsync(projectId, userId, UserName);
```

### ۱۰.۵ جریان کامل (پیام چت)

```
۱. کاربر A پیام ارسال می‌کند
         ↓
۲. ChatHub.SendMessage()
         ↓
۳. پیام در دیتابیس ذخیره
         ↓
۴. ├── SignalR → کاربران آنلاین (بلادرنگ)
   └── Webpushr → کاربران آفلاین (Push)
         ↓
۵. WebpushrService → لیست اعضای پروژه
         ↓
۶. برای هر عضو (بغیر از فرستنده):
   └── SendWebpushrNotification()
         ↓
۷. POST به api.webpushr.com:
   { "title": "نام فرستنده", "message": "متن پیام", "sid": 12345 }
         ↓
۸. 🔔 اعلان در ویندوز/موبایل نمایش داده می‌شود!
```

### ۱۰.۶ ثبت در Program.cs
```csharp
builder.Services.AddScoped<IWebpushrService, WebpushrService>();
```
